# اسپرینت ۱۱ — حلقه زمان‌بندی Handler / Cron

**نوع سند:** دستورکار معماری موتور زمان بازی (فقط مستند)  
**منبع تحلیل:** `Cron.php` / `cron.php` / `Handler.php` / `HL::CheckTimer` / `HL::checkTime` / `HL::CheckEndGame`  
**هم‌وابسته:** اسپرینت ۱ (شب)، ۷ (روز)، ۸ (رأی)، ۲ (گاز در مرز رأی→شب)، ۴ (برد)

---

# ۱. تحلیل و استدلال

ربات دو مسیر ورودی دارد که نباید یکی فرض شوند:

1. **Webhook (Hook / Commands / CM)** — فقط وقتی تلگرام آپدیت می‌فرستد: جوین، رأی، انتخاب شب/روز، تنظیمات. انتخاب‌ها معمولاً فقط در Redis ذخیره می‌شوند.  
2. **Cron → cron → Handler** — تیک دوره‌ای برای هر سشن فعال گروه؛ مستقل از اینکه کسی چت کند یا نه.

بازی ورولف **ساعت‌محور** است: مدت شب/روز/رأی، حل فاز در پایان تایمر، وقفه‌های +۳۰/+۴۵ ثانیه، AFK، اعمال گاز تأخیری، و اعلام برد خودکار همه به تیک زمان نیاز دارند. اگر فقط webhook باشد، فاز فقط با «شانس پیام کاربر» جلو می‌رود و سکوت گروه = توقف بازی.

نام‌گذاری: کلاس `cron` کانتکست یک گروه/بازی است (Redis، Mongo، Lang). کلاس `Handler` یک تیک همان کانتکست را اجرا می‌کند. فایل ورودی زمان‌بندی (`Cron.php` و مشابه) لیست بازی‌های فعال را می‌گیرد و برای هرکدام یک `cron` + `Handler::Handel` راه می‌اندازد.

`CronJob` آمار/شرط‌بندی جداست و جایگزین موتور فاز نیست.

---

# ۲. آیا بودنش لازم است؟

**بله — برای این معماری لازم است.**

بدون حلقه زمان‌بندی جدا (یا معادل آن: worker/queue با job تأخیری):

- `timer` به پایان نمی‌رسد مگر کسی آپدیت بفرستد  
- `CheckNight` / `CheckDay` / `CheckVote` سر وقت اجرا نمی‌شوند  
- انتقال night→day→vote→night می‌شکند  
- `BittanCheck` در مرز رأی→شب تضمین نمی‌شود  
- `CheckEndGame` / `GamedEnd` در سکوت گروه رخ نمی‌دهد  
- early-end، وقفه توله/کلانتر/رویس، شمارش لابی جوین، DontVote/AFK ناپایدار می‌شوند  

**جایگزین معتبر معماری:** همان مسئولیت را با صف تأخیری خارجی (مثلاً job «در timestamp X فاز را حل کن») پیاده کنید. باز هم یک زمان‌بند جدا از webhook دارید؛ فقط پیاده‌سازی Cron کلاسیک نیست. حذف کامل زمان‌بند = تغییر مدل محصول به بازی غیردوره‌ای، که با طراحی فعلی PHP سازگار نیست.

# ۳. جریان یک تیک (رفتارشناسی)

برای هر سشن فعال تقریباً این ترتیب اجرا می‌شود:

### ۳.۱ ورود و قفل
1. خواندن `game_state`  
2. اگر `GamePl:InComplater` باشد → خروج (جلوگیری از دو تیک هم‌زمان روی یک گروه)  
3. اگر `GamePl:GameIsEnd` باشد → خروج  
4. ست `InComplater` با TTL حدود ۲۰ ثانیه  

### ۳.۲ شاخه فازهای در جریان (night / day / vote)
1. پاک‌سازی قفل کهنه `CheckNight` اگر بیش از `night_timer` مانده باشد  
2. `CheckSmite`  
3. اگر `HunterKill` باز نباشد: `CheckEndGame`؛ در صورت برنده و وجود `RoleAssinged` → `GamedEnd` و پایان تیک  
4. اگر نفرین مرگ ملکه جنگل برای همین شب نباشد و `HunterKill` نباشد: `checkTime` (پایان زودهنگام تایمر)  
5. `CheckTimer` — اگر `timer` تمام شده:  
   - night → `CheckNight` سپس در نبود وقفه → day  
   - day → `CheckDay` سپس → vote  
   - vote → `CheckVote` سپس `BittanCheck` سپس → night (+ افزایش شمارنده‌ها، پاک‌سازی فلگ‌های زمان‌دار)  

وقفه‌هایی که انتقال را عقب می‌اندازند (از جمله): `HunterKill`, `SendWolfCubeDead`, `RoyceSelectd2`, `StopBlack` (مسیر مرده — طبق مرتفع‌سازی باید fix شود), `trouble` برای رأی دوم.

### ۳.۳ جادو
اگر کلیدهای `UseMajik:*` باز باشند → `HandelMajik`.

### ۳.۴ هندلر فاز جاری
| `game_state` | فراخوانی |
|--------------|----------|
| join | `join::Handel` — لابی، شمارش معکوس، شروع |
| night | `NG::Handel` — ارسال کیبورد شب، اعلام شکارچی، … |
| day | `DY::Handel` — پیام عشق/کیبورد روز |
| vote | `VT::Handel` — ارسال/به‌روز رأی |

### ۳.۵ خروج
پاک کردن `InComplater`.

Webhook در همان لحظه فقط `Selected` / دستورات را می‌نویسد؛ اثر مرگ و عوض فاز عمدتاً در همین تیک (یا تیک بعدی پس از صفر شدن تایمر) دیده می‌شود.

# ۴. قراردادهای زمانی مهم

| مفهوم | نقش |
|--------|-----|
| `timer` | timestamp پایان فاز جاری |
| `night_timer` / `day_timer` / `vote_timer` / `secret_timer` / join timer | مدت تنظیم‌شده |
| `checkTime` | early-end: مثلاً شب پس از نصف مدت اگر همه انتخاب کرده باشند |
| `PlusTime` / افزودن به timer | وقفه‌ها (+۴۵ توله/کلانتر، +۳۰ رویس، …) |
| `InComplater` | قفل تک‌نویسی تیک |
| `CheckNight` / `CheckDay` / `CheckVote` | قفل یک‌باره حل فاز |

خواب‌گذار می‌تواند هنگام ورود به شب `timer = 0` کند تا تیک بعدی شب را فوری resolve کند.

---

# ۵. امکانات و بهبودی که این حلقه می‌دهد

| امکان | بدون زمان‌بند جدا | با Handler/Cron (یا معادل queue) |
|--------|---------------------|----------------------------------|
| فاز سر وقت | وابسته به پیام تصادفی | قطعی |
| پایان زودهنگام وقتی همه انتخاب کردند | practically ندارد | طبیعی با `checkTime` |
| وقفه‌های زمانی نقش‌ها | شکننده | کنترل‌شده با تمدید `timer` |
| اعلام برد در سکوت گروه | نمی‌آید | در همان تیک‌ها می‌آید |
| چند گروه موازی | منطق فاز قاطی webhook می‌شود | هر سشن تیک جدا + قفل |
| مقیاس و تست | I/O تلگرام و موتور یکی | جداسازی ورودی کاربر از موتور ساعت |
| لابی معکوس‌شمار | فقط با اسپم جوین جلو می‌رود | تیک‌های منظم پیام ۶۰/۳۰/۱۰ |

### منافع محصولی
- بازی عادلانه‌تر: کسی با سکوت چت نمی‌تواند فاز را نگه دارد (جز AFK رسمی).  
- تجربه نرم‌تر: شب/روز بدون نیاز به «یک نفر چیزی بفرستد تا Cron معنا پیدا کند».  
- پایداری چندگروه: قفل `InComplater` از double-resolve جلوگیری می‌کند.  
- پایهٔ پورت پایتون: می‌توان همان قرارداد را با Celery/RQ/ARQ/cron K8s پیاده کرد؛ **نقش معماری ثابت می‌ماند**.

# ۶. مرز با مسیرهای دیگر

| مسیر | مسئولیت |
|------|----------|
| Webhook / CM | نوشتن انتخاب، جوین/فرار، کانفیگ، پاسخ کال‌بک |
| Handler تیک | خواندن تایمر، حل فاز، برد، ارسال کیبورد فاز |
| `CronJob` | آمار/بت جانبی — موتور فاز نیست |
| مرتفع‌سازی StopBlack | تایمر امروز فلگ مرده می‌خواند؛ پس از fix، وقفه سیاه هم در همین حلقه resolve می‌شود |

قانون طلایی بازنویسی: **webhook هرگز به‌تنهایی CheckNight/CheckDay/CheckVote را جایگزین تیک نکند** مگر همان کد پشت یک job زمان‌بندی‌شده صدا زده شود.

# ۸. جمع‌بندی یک‌خطی

حلقه Handler/Cron **موتور ساعت بازی** است؛ بودنش برای ورولف تایمردار الزامی است (یا معادل queue). امکان اصلی‌اش: جلو رفتن قطعی فازها، برد، وقفه‌ها و لابی — مستقل از شلوغی چت — به‌همراه ایزوله کردن ورودی تلگرام از منطق زمان.
